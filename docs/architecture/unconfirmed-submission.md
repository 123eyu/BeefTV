# 提交结果不明时怎么收尾：方案与计划

适用范围：画布图片、视频、超分、配音任务。内置渠道指用 BeefTV 账号连接的 BeefAPI；BYOK 指用户自带 Key 的第三方渠道（协议插件）。

## 一、问题：节点为什么会锁住

点「生成」后，请求发出去了，但没收到明确回复（网络超时、5xx、连接中断）。这时 BeefTV 不知道上游有没有开始生成、有没有扣钱。如果马上允许「重新生成」，原来那次可能已经在跑、已经扣费，用户就会付两次钱、拿到两份结果。所以节点会隐藏「重新生成」，只留「继续取回」，等查清原任务的下落：查到结果就放回画布，查到确实失败就解锁。

锁本身是为了保护用户，问题在于有的情况永远查不清。客户遇到的「节点锁死」（飞书 #108，v2.0.6 验收 ISSUE-2、ISSUE-6）都属于这一类：节点上只剩一个点了也没用的「继续取回」，只能删掉节点重做。

## 二、原则

1. **结论由能知道的一方给。** 内置渠道「收没收到、扣没扣钱」只有 BeefAPI 知道；BYOK 只有供应商知道，BeefTV 通过协议插件声明的能力去问。
2. **锁必须有终点，锁住期间必须有一条不会多扣钱的出路。**
3. **渠道能力写在协议声明里**（BeefAPI 响应头、插件 manifest），不按模型名或域名判断（AGENTS.md 第 10 节）。
4. **能不能重试、能不能取回只在后端 `task.outcome` 一处计算**，前端照读。

## 三、业界做法：幂等编号

「请求发出去了、没收到回复」的通用解法是幂等编号：客户端提交时自带一个编号，服务端记住这个编号第一次的结果；之后拿同一个编号再提交，服务端返回第一次的结果，不会再执行一次。客户端遇到超时就可以放心重发，不需要等，也不需要锁。

- Stripe：同一个 `Idempotency-Key` 的重复请求返回第一次保存的状态码和响应体；参数不同则报错；键至少保留 24 小时。
- Google AIP-155：请求带 `request_id` 时服务端必须保证幂等，重复请求通常返回第一次的响应。
- AWS Bedrock `StartAsyncInvoke`：用 `clientRequestToken` 防止重复创建。
- BeefAPI 自己的视频提交（`docs/specs/video-unknown-recovery-2026-09-20.md`）：同编号重试返回原任务；结果不明设截止时间，到期自动退款。

## 四、现状（2026-10-31 核对代码）

### 4.1 内置 BeefAPI

| 事实 | 位置 |
| --- | --- |
| BeefTV 发出托管媒体请求前，把完整原请求（地址、请求头含原 Key 与 `Idempotency-Key`、请求体）加密冻结，保留 23 小时（`RecoveryLifetime`），之后只留查询用的部分 | `beefapi/media.go` `Execute` 的 `State.Begin`；`mediaattempt/image_submission.go` |
| BeefAPI 按（站点、账号、Key、编号）去重：同编号同内容返回原任务（`Idempotency-Replayed: true`），内容不同返回 409 `idempotency_conflict`；编号记录不删除 | BeefAPI `middleware/image_submission.go`、`middleware/video_submission.go` |
| 托管视频、超分、配音必须开启 `VIDEO_SUBMISSION_GUARD_ENABLED` 才能提交，所以线上能用就说明去重在生效 | BeefAPI `middleware/media_task.go` |
| BeefAPI 视频结果不明 30 分钟（`VIDEO_RECONCILE_DEADLINE_SECONDS`）仍没拿到上游任务号，自动全额退款、任务判失败 | BeefAPI `docs/specs/video-unknown-recovery-2026-09-20.md` C1 |
| BeefAPI 图片提交 10 分钟后仍无结果，查询返回 `media_result_unknown`，任务记为「对账中」；同一个每分钟对账扫描在 30 分钟后自动全额退款（没有上游任务号时）；24 小时后查询返回 `media_result_expired` | BeefAPI `service/media_task_projection.go`、`service/managed_image_task.go`、`service/video_reconcile_deadline.go` |
| BeefAPI 查询返回 404 `media_task_not_found`：这把 Key 下没有这个编号的记录，也可能是记录存在但当前不可见；BeefAPI 明说这不代表没提交 | BeefAPI `controller/media_task.go` |
| **BeefTV（本次修改前）**：托管任务的恢复只查询、从不补交。查询 404 时不下结论：图片无限期等，视频最多等 7 天；期间节点只有「继续取回」 | `mediaattempt/image_auto_recovery.go`、`mediaattempt/managed_media.go` |

结论：BeefAPI 已经具备「同编号重发不重复扣费」和「结果不明 30 分钟内结案退款」的能力，BeefTV 的托管接口没有用上前者。会长期锁住的只剩一种情况：**BeefAPI 根本没收到原请求**（查询 404）。

### 4.2 BYOK

- 没拿到供应商回执（任务号）：马上判为「无法取回」，节点解锁，重新生成前要确认一次。
- 拿到了任务号：按任务号查询，直到出结果或超过渠道保留期（现为 24 小时）。
- 插件 manifest 目前没有「上游按编号去重」「可按我方编号查询」的声明。仓库里只有 `full-video` 插件映射了 `Idempotency-Key`，上游是否去重未核实。
- 火山方舟有任务列表接口，但只能按任务号、状态列，不能按我方编号查，最多只能列出来让用户自己认，不能自动对上。

## 五、方案

### 5.1 内置 BeefAPI：用原编号补交（本次实现）

用户点「继续取回」，BeefTV 用原 Key 查询原编号：

| 查询结果 | 处理 |
| --- | --- |
| 查到任务（排队、生成中、完成、失败） | 照现在的流程处理 |
| 404，原请求仍在 23 小时保存期内，本地没有 BeefAPI 结算记录 | 用原 Key、原编号、原内容把冻结的原请求**补交一次**。BeefAPI 收到过就返回原任务；没收到才第一次执行，也只扣这一次 |
| 404，原请求已超过保存期 | 已经无法补交，也无法确认。结论记为「无法取回」，节点解锁，重新生成前需要确认 |
| 404，但本地已有 BeefAPI 结算记录 | BeefAPI 记过这次提交，只是暂时不可见。不补交，继续等 BeefAPI 的结论 |

补交的返回：

| 返回 | 结论 |
| --- | --- |
| 成功（原任务或刚创建的任务） | 不写结论；托管图片 15 秒后再查，视频当场再查一次；出结果后自动写回画布 |
| BeefAPI 给出失败，或拒绝请求内容、余额不足（400、402、413、422） | 「没有结果」：这次补交没执行，原请求也从没被收到 |
| 409 `idempotency_conflict`，或 Key 失效、无权限、地址不存在（401、403、404） | 「无法取回」：只说明补交本身失败，不能证明原请求没执行，重新生成前确认 |
| 5xx、超时、409 `video_submission_pending` | 不写结论，用户可以再点一次 |

约束：

- **只在用户手动「继续取回」时补交。** 手动标记只由 `POST /api/tasks/:id/recover` 的处理函数打上（`task.WithManualRecovery`），`RecoverTask` 本身不打；后台自动恢复只查询、不补交，避免原请求没到达时，几小时后突然开始生成、突然扣费。
- 补交用冻结的原 Key，所以客户之后换了 BeefAPI Key 也不会被当成新提交。
- **查询得到的 404 和提交得到的 404 是两种错误。** 查询原编号的 404 是 `beefapi.MediaTaskMissingError`，永远不算「明确被拒」；提交的 404 才是 `MediaHTTPError`。生成过程（含重启后接着跟进原提交）查不到时继续等，因为原请求可能还在路上；只有失败任务的恢复（`RecoverManagedImage`、视频查询）会处理「查不到」。
- 「超过保存期仍 404 就判无法取回」后台也会做，没人点也会解锁；冻结原请求是否过期只由 `mediaattempt.FrozenRequestExpired` 判断。
- 已下的「无法取回」保持不变：托管图片每小时向 BeefAPI 复查一次，仍查不到就维持结论，能查到就按 BeefAPI 的结论纠正。
- 视频的这条规则先于「无结算记录的托管视频等 7 天」：BeefAPI 收到的视频提交 30 分钟内就会结案，原 Key 过了 23 小时还查不到，说明它没有这条记录。其他未知响应（5xx 等）仍按 7 天。
- 配音节点同样走这套恢复（`RecoverTask` 把 `canvas_audio` 交给媒体恢复）。
- BeefAPI 错误的语义（是否终态、是否明确拒绝、是否查不到）只在 `beefapi` 包判断一处，调用方只读结论。

用户看到的文案：

- 点了「继续取回」但结果还没出来：「原任务还在确认中，有结果后会自动放回画布」。
- 「无法取回」：「无法确认上次是否已扣费，可先到渠道后台查看使用记录」，重新生成前确认「重新生成可能会再扣一次」。

### 5.2 BeefAPI（核实后暂不需要改）

1. 原计划给图片补「结果不明到期退款」。核对代码后发现已经有了：对账扫描不区分图片和视频，托管图片结果不明且没有上游任务号时，30 分钟后自动全额退款。
2. 待确认：图片已拿到上游任务号又停在「对账中」时，扫描会走视频专用的挽救逻辑（`RescueVideoTaskIdentity`），对图片是否适用尚未核实。
3. 可选：查询 404 区分「从没收到这个编号」和「记录存在但当前不可见」。前者可以作为确定结论，BeefTV 能马上解锁、不必补交。有了 5.1 的补交后不急。

### 5.3 BYOK

1. 现有行为保持：没回执马上解锁（重新生成前确认），有回执查到保留期。
2. 文案补上「可先到渠道后台查看使用记录」（本次，与 5.1 共用）。
3. 后续：插件 manifest 声明三项能力，由插件作者负责，后端按声明启用（`generation-task-state.md` 第 3.2、3.7 节已提出）：
   - 上游是否按我方编号去重：是则结果不明时用同一编号补交，和 5.1 相同；
   - 能否按我方编号查询；
   - 结果保留期：决定查询截止时间。
   可灵的自定义任务号能不能用来查询，目前没有找到官方文档确认，接入前要实测。

## 七、已知不能解决的

- 409 `idempotency_conflict` 之后，后续仍按同一编号查询，理论上可能查到占用这个编号的另一份内容。BeefTV 的编号按任务和尝试生成，同一账号、同一 Key、同一编号出现不同内容需要 BeefTV 自身先出错；这也是原有「按编号查询」机制的边界，不是补交引入的。

- BeefAPI 的结论本身错了，BeefTV 照读，不复核。
- 原请求超过 23 小时还没人点「继续取回」，就不能再补交，只能让用户确认后重新生成。
- BYOK 供应商不支持按编号去重、又没给回执时，BeefTV 无法知道是否扣费，只能把判断交给用户。

## 八、真实画布验证结果（2026-10-31，Mac，独立数据目录）

用 CUA 操作 `/Applications/BeefTV.app`（本分支打包），在画布节点上直接点「生成」，模型 Seedance 2.0 Fast、480P、16:9、4 秒，共 4 条。

| 场景 | 做法 | 结果 |
| --- | --- | --- |
| 正常完成 ×2 | 点生成后不打断 | 视频回到原节点；每个任务 1 次创建请求、1 次查询 |
| 生成中退出再打开 | 拿到上游任务号后 Cmd+Q 退出，等 1 分钟重开 | 后台接上原任务，结果回到原节点；原请求只发出 1 次（`send_count = 1`），任务结算为已结算，没有新增任务 |
| 结果落地时节点有未保存编辑 | 生成中和完成后每 8 秒往同一节点的输入框追加文字 | 结果回到原节点；12 段文字全部保存在 `composerContent`；没有出现版本冲突 |
| 生成中刷新页面 | Cmd+R | **桌面版做不到**：没有 Cmd+R 和「重新加载」菜单，页面只在报错页、改存储设置等情况下由程序刷新。这一项由前端浏览器测试 `canvas-late-generation-recovery` 覆盖 |
| 两个窗口同时编辑 | 画布菜单「在新窗口打开」 | 入口只在鼠标悬停时出现，CUA 后台操作打不开，未验证 |

「BeefAPI 没收到原请求、手动继续取回补交」无法在真实客户端里制造，由后端测试覆盖（`managed_resubmit_test.go`）。
